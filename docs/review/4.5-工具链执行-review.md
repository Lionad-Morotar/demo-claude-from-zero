# 修改建议: 4.5 工具链执行

## 综合评估
- 整体质量: 官方引用比例较高(6/10)，大量CLI命令和flag被证实真实存在。但Hooks JSON格式错误、Monitor工具误标为内置、安全示例配置过度宽松是主要问题
- 问题分布: 🔴 高 4 / 🟡 中 5 / 🟢 低 3
- 是否阻塞发布: 否（修正Hooks格式 + 删除Monitor误标 + 收紧安全示例后可发布）

## 🔴 必改(高优先级:事实错误、逻辑硬伤)

### 1. Monitor 不是内置工具，是插件组件
- **位置**: 第 1.1 节 / 第 28 行、第 8 节
- **原文摘录**:
  > "命令执行: `Bash`（执行 Shell 命令）、`PowerShell`（Windows 原生 PowerShell 执行）、`Monitor`（后台监控）"
- **问题**: 官方插件参考文档将 **monitor 列为插件组件**（与 skills、agents、hooks、MCP servers、LSP servers 并列），而非 Claude Code 内置工具。文档将 Monitor 与 Bash/PowerShell 并列作为"内置工具"是**错误的**，第 8 节整节"Monitor 工具:后台任务监控"建立在错误前提上。
- **建议改写**:
  - 1.1 节: 将 Monitor 从"内置工具"列表中移除，改为在"扩展能力"小节中提及："Monitor（通过插件系统启用，用于后台任务监控）"
  - 第 8 节: 在标题添加标注"（需通过插件启用）"，或整节移至"扩展与插件"章节
- **依据**: https://code.claude.com/docs/en/plugins-reference（web-searcher 核实，monitor 为插件组件）

### 2. Hooks JSON 数组格式与官方规范不符
- **位置**: 第 7.4 节
- **原文摘录**:
  ```json
  {
    "hooks": [
      {
        "event": "PreToolUse",
        "matcher": { "tool": "Bash", "pattern": "rm -rf /*|DROP TABLE|DELETE FROM.*WHERE" },
        "command": "echo '{\"decision\": \"deny\", \"reason\": \"Dangerous command blocked\"}' && exit 2"
      }
    ]
  }
  ```
- **问题**: 官方 Hooks 格式为 `"hooks": { "PostToolUse": [...], "PreToolUse": [...] }` **对象形式**（事件名为键），不是数组形式。文档使用了 `"hooks": [...]` 数组格式，与官方 schema 不符。`exit 2` 控制权限的机制也未在官方文档中确认。这与 4.3 节和官方文档均不一致。
- **建议改写**: 修正为官方对象格式：
  ```json
  {
    "hooks": {
      "PreToolUse": [
        {
          "matcher": "Bash(rm -rf /*|DROP TABLE|DELETE FROM.*WHERE)",
          "hook": "echo 'Dangerous command blocked' && exit 2"
        }
      ]
    }
  }
  ```
  并添加注释："Hooks 格式请以官方文档为准: https://code.claude.com/docs/en/hooks"
- **依据**: https://code.claude.com/docs/en/hooks ; https://code.claude.com/docs/en/setup（web-searcher 核实）

### 3. 安全示例配置过度宽松，提供危险的 copy-paste 模板
- **位置**: 第 2.3 节 Docker、第 2.4 节 Kubernetes、第 5.3 节 GCP/Azure、第 9.1-9.2 节
- **原文摘录**:
  - `"Bash(docker exec *)"` 放在 allow
  - `"Bash(kubectl get *)"` 放在 allow（包含 `kubectl get secrets`）
  - `"Bash(gcloud *)"`、`"Bash(az *)"` 放在 allow
  - `"allowWrite": ["~/.kube"]`
- **问题**: 这些示例在"安全"章节中出现，实际上提供了危险的 copy-paste 模板：
  - `docker exec *` 允许在任意容器中以任意身份执行任意命令，等同于 root 权限
  - `kubectl get *` 包含 `kubectl get secrets`，直接暴露集群敏感凭证
  - `gcloud *`、`az *` 无差别访问所有云资源
  - `allowWrite: ["~/.kube"]` 允许写入集群认证配置
- **建议改写**: 将所有过度宽松的规则收紧：
  ```json
  // Docker: 将 docker exec 从 allow 移至 ask
  "ask": ["Bash(docker exec *)"]
  // Kubernetes: 限制 get 范围，secrets 单独处理
  "allow": ["Bash(kubectl get pods|services|deployments *)"],
  "ask": ["Bash(kubectl get secrets *)"]
  // 云厂商 CLI: 限制为只读操作
  "allow": [
    "Bash(gcloud compute instances list)",
    "Bash(az resource list)"
  ]
  ```
- **依据**: challenger [A]

### 4. LSP 工具描述完全准确，challenger 质疑错误
- **位置**: 第 3.3 节
- **原文摘录**:
  > "Claude Code 的 `LSP` 工具在每次文件编辑后自动报告类型错误和警告。这消除了单独的编译步骤..."
- **问题**: challenger [2] 质疑 LSP 是"显式调用"而非"自动报告"，但 **官方工具参考明确确认** "After each file edit, it **automatically reports** type errors and warnings"。challenger 的质疑与官方文档直接矛盾。
- **建议改写**: **无需修改**，当前描述准确。但可补充引用来源：
  > "Claude Code 的 `LSP` 工具在每次文件编辑后自动报告类型错误和警告[^X]。这消除了单独的编译步骤..."
- **依据**: https://code.claude.com/docs/en/tools-reference（web-searcher 核实）

## 🟡 建议改(中优先级)

### 5. Skill frontmatter 字段存疑
- **位置**: 第 6.1 节
- **原文摘录**:
  ```markdown
  ---
  name: pr-summary
  description: Summarize changes in a pull request
  context: fork
  agent: Explore
  allowed-tools: Bash(gh *)
  ---
  PR diff: !`gh pr diff`
  ```
- **问题**: `name`、`description`、`tools` 是官方支持的 frontmatter 字段。但 `context`、`agent`、`allowed-tools` 字段和 `!`command`` 语法在公开搜索中未找到官方文档确认。
- **建议改写**: 在 Skill 示例前添加注释：
  ```markdown
  <!-- 以下为示意性 Skill 配置，具体 frontmatter 字段请以官方文档为准 -->
  <!-- https://code.claude.com/docs/en/skills -->
  ---
  name: pr-summary
  description: Summarize changes in a pull request
  ---
  ```
- **依据**: https://code.claude.com/docs/en/skills（web-searcher 核实，未找到 context/agent/allowed-tools 字段）

### 6. MCP 配置位置前后不一致
- **位置**: 第 4.1 节、第 9.2 节
- **原文摘录**:
  - 4.1 节: "配置 `.mcp.json`"
  - 9.2 节: `"mcpServers": { ... }` 放在 JSON 根字段下
- **问题**: 4.1 节使用 `.mcp.json`，9.2 节放在 settings.json 的 `mcpServers` 字段下，前后不一致。MCP 配置通常放在 `settings.json` 的 `mcpServers` 字段中。
- **建议改写**: 统一为 `settings.json` 中的 `mcpServers` 字段，删除 `.mcp.json` 的提法。
- **依据**: web-searcher 核实，未找到 `.mcp.json` 的官方推荐

### 7. `auto` 权限模式描述不准确

## 🟢 可选改(低优先级)

### 10. "核心竞争力"表述商业化

- **原文摘录**: "Claude Code 的核心竞争力"

### 11. `docker exec` 与包装器剥离段落逻辑不通
- **位置**: 第 7.1 节
- **原文摘录**: "`direnv exec`、`devbox run`、`mise exec`、`npx`、`docker exec` 不在剥离列表中"
- **问题**: `docker exec` 根本不是"包装器(wrapper)"，把它和 `npx`、`direnv` 并列逻辑不通。
- **建议改写**: 将 `docker exec` 从列表中删除，或单独说明 "`docker exec` 是容器内命令执行机制，不属于包装器剥离范围"
- **依据**: challenger [I]

### 12. `Bash(* --version)` 和 `Bash(* --help *)` 违反最小权限
- **位置**: 第 9.1 节
- **原文摘录**: `"Bash(* --version)"`、`"Bash(* --help *)"` 放在 allow
- **问题**: 虽然 `--version` 通常无害，但这种通配符模式违反了"最小权限原则"，与第 7.6 节第 1 条"从严格开始"直接矛盾。
- **建议改写**: 删除这两个通配符规则，或移至说明文字中："大部分只读命令（如 `--version`/`--help`）通常安全，但仍建议按需显式授权"
- **依据**: challenger [K]

## 💡 建议补充

### 13. 补充交互式命令处理
- **位置**: 第 2 节
- **建议**: 文档未讨论 `npm init`、`docker run -it` 等需要 TTY/交互式输入的命令在 Claude Code 中如何处理。这是一个高频痛点。建议补充：
  - Claude Code Bash 工具不支持交互式输入（无 TTY）
  - 需要使用 `--yes`、`-y`、`--non-interactive` 等免交互标志
  - 或预先通过环境变量/配置文件提供所需输入
- **依据**: challenger [N]

### 14. 补充工具执行超时处理
- **位置**: 第 2 节
- **建议**: Claude Code Bash 工具有默认超时（约 2 分钟），长运行任务（如大型构建、数据库迁移）可能超时。建议补充：
  - 使用 `nohup` 或后台进程处理长任务
  - 使用 Monitor 插件（如已启用）追踪长任务进度
  - 或分步执行避免单次超时
- **依据**: challenger [N]

### 15. 补充环境变量注入讨论
- **位置**: 第 2 节
- **建议**: 除了 `CLAUDE_ENV_FILE`，未讨论 `.env` 文件加载、`direnv` 等实际开发中常用的环境管理方式。建议补充：
  - 使用 `direnv` 自动加载项目环境变量
  - 在 `settings.json` 中通过 `env` 字段注入环境变量
- **依据**: challenger [N]

## 📚 原文优点(明确保留)

1. **LSP 自动诊断描述准确**: 官方工具参考明确确认 LSP 在每次文件编辑后"automatically reports type errors and warnings"，文档描述完全正确，challenger [2] 的质疑被推翻。
2. **大量 CLI 命令和 flag 被证实**: `claude "query"`（位置参数）、`claude -p`、Seatbelt/bubblewrap 沙箱、`auto` 权限模式——全部真实存在。
3. **权限规则语法详细**: 7.1 节的路径模式类型（`//path`、`~/path`、`/path`）、通配符规则、进程包装器剥离等细节准确且实用。
4. **沙箱隔离描述准确**: 7.2 节的文件系统隔离、网络隔离、OS 级执行技术（Seatbelt/bubblewrap）均有官方文档支撑。
5. **MCP 传输类型覆盖完整**: 6.2 节的 stdio、HTTP/SSE、SDK 内嵌三种传输类型描述清晰，MCP 工具命名规则准确。
