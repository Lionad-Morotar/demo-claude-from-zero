# Review: 6.3-核心功能实现-多轮迭代开发.md

## 🔴 必改

### [R1] `claude --plan-mode` 完全虚构（事实错误）
- **位置**: 第 3.3 节 / 第 218 行
- **问题**: 使用 `claude --plan-mode` 作为 Plan 模式启动命令
- **核实结果**: 官方文档确认的 Plan 模式启动方式只有 `claude --permission-mode plan`。`--plan-mode` 这个 flag 不存在
- **修改建议**: 改为 `claude --permission-mode plan`。这与 6.1 章 `/plan exit`、5.4 章的相关错误形成一致模式——全书 Plan 模式命令需统一审查

### [R2] 伪数据泛滥（全书最严重之一）
- **位置**: 全文多处，第 30、53、488、550、735 行等
- **问题**: 至少 15 个精确数字（8-15 分钟、30-60 分钟、3-4 倍、60-90 分钟、500 行、80 行、≥30 分钟、≤5 分钟、8%、<1%、3-7 轮、30-80 行、<5%、<2%、3-10 条、>团队人数×5、<30 分钟/人/天、95%）全部标注为"本人经验"，但没有任何样本量、统计方法或项目背景说明
- **修改建议**: 删除所有未经证实的精确数字，改为定性描述或明确标注"作者个人经验估计"。具体：
  - "8-15 分钟"→"通常明显快于传统模式"
  - "3-4 倍"→"显著提速"
  - "健康范围"→"参考阈值（需团队自行校准）"
  - "覆盖率 95%"→删除数字，改为"增加 repository 单元测试"

### [R3] "一次成型"稻草人论证
- **位置**: 第 1.1 节 / 第 30-35 行
- **问题**: 将"一次成型"极端化为"≥500 行代码、≥30 分钟审查"，现实中现代软件工程（CI/CD、Git 最佳实践、敏捷开发）早已提倡小步提交
- **修改建议**: 承认现代工程实践早已提倡小步提交，Claude Code 是增强了这一实践而非发明了它。将对比表改为"传统 IDE 辅助下的迭代"vs"Claude Code 协作下的迭代"，删除极端数字

### [R4] Hindsight TODO 注释虚构前瞻性
- **位置**: 第 4.4 节 / 第 466 行
- **问题**: `// TODO: 第 5 轮重构为类` 注释是典型的 hindsight 编写。在真实第 4 轮迭代中，作者不可能预先知道第 5 轮要做什么
- **修改建议**: 删除该 TODO 注释，或改为更诚实的表述，如"当前实现是模块级 Map，未来如需更复杂的生命周期管理可考虑重构为类"

## 🟡 建议改

### [Y1] "3-4 倍提速"和"1/4 时间"夸大
- **位置**: 第 1.2 节 / 第 53 行；第 4.6 节 / 第 528 行
- **问题**: 声称"3-4 倍提速"、"相当于工程师独立开发的 1/4"。即使 Claude 能加速编码环节，需求理解、架构设计、代码审查、测试设计、与利益相关者沟通等环节并不会消失
- **修改建议**: 改为"在编码实现环节显著提速"，并补充说明"整体项目周期受需求、设计、沟通等环节制约，AI 协作主要压缩的是编码实现时间"

### [Y2] "健康范围"将个人偏好伪装成科学标准
- **位置**: 第 6.3 节 / 第 735-741 行

- **修改建议**: 删除与"独立开发"的对比，改为强调"可追溯的历史"和"审查质量的提升"这些多轮迭代真正的优势

- **问题**: 将个人工作习惯（番茄钟）推广为团队标准，没有解释依据
- **修改建议**: 改为"建议团队通过实践找到适合自身的会话长度，作者个人经验是 60-90 分钟"

### [G3] 6 轮迭代总耗时假设不严谨
- **位置**: 第 4.6 节 / 第 528 行

- **修改建议**: 添加脚注说明这是理想条件下的估算，实际耗时受网络、模型响应速度、审查深度等因素影响

## 💡 建议补充

### [S1] Token 经济性
- **缺失内容**: Claude Code 的 API 调用是有成本的，多轮迭代可能增加 token 消耗
- **建议**: 补充 token 成本分析，包括多轮迭代 vs 一次成型的 token 消耗对比、成本优化策略（如使用缓存、控制上下文长度）

### [S2] 代码质量退化风险
- **缺失内容**: 多轮迭代虽然每次提交小，但累积的局部优化可能导致整体架构腐化（code rot）
- **建议**: 补充"迭代债务"概念，讨论如何通过定期重构、架构 review 防止局部优化导致的全局腐化

### [S3] 过度迭代的判断标准
- **缺失内容**: 什么时候应该停止迭代？文档没有给出判断标准
- **建议**: 补充"迭代终止条件"，如"达到验收标准"、"边际收益低于边际成本"、"遇到架构级问题需升级决策"

### [S4] 失败案例
- **缺失内容**: 整章没有呈现任何"多轮迭代失败后不得不重来"的真实案例
- **建议**: 补充一个失败案例，如"迭代到第 8 轮发现最初的数据模型假设错误，不得不回滚到第 2 轮重来"，增强现实感

### [S5] 团队协调
- **缺失内容**: 当不同工程师对"一轮迭代应该多小"有不同偏好时，如何协调？
- **建议**: 补充团队迭代规范的制定方法，如通过 retro 会议达成共识、使用 CLAUDE.md 固化团队标准
