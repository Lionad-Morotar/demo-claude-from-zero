# Review: 6.2-项目脚手架搭建与技术选型.md

## 🔴 必改

### [R1] MCP 包名完全虚构（最严重的事实错误）
- **位置**: 第 2.5 节 / 第 224-235 行
- **问题**: 示例中使用 `@modelcontextprotocol/server-npm` 和 `@upstash/context7-mcp` 两个 MCP 包名
- **核实结果**: 两个包在 npm registry 上均**无法找到**。`modelcontextprotocol/servers` 官方仓库中没有 npm registry server 实现。context7.com 虽是真实服务，但未发布名为 `@upstash/context7-mcp` 的 MCP Server 包
- **修改建议**: 立即删除该示例，或替换为经核实的 MCP 包名。如需保留 context7 功能说明，应改为"context7 提供实时文档查询服务"，删除具体的不可运行 MCP 配置代码

### [R2] Nuxt 初始化命令过时
- **位置**: 第 1.2 节 / 第 39 行
- **问题**: 使用 `pnpm create nuxt-app` 作为 Nuxt 初始化命令
- **核实结果**: Nuxt 3/4 的官方推荐初始化命令是 `npx nuxi@latest init` 或 `npx create-nuxt-app`。`pnpm create nuxt-app` 指向旧的 `create-nuxt-app` 包，可能得到与预期不符的项目结构
- **修改建议**: 将 `pnpm create nuxt-app` 改为 `npx nuxi@latest init`（或 `pnpm dlx nuxi@latest init`），并标注 pnpm 等价写法

### [R3] ESLint v9 flat config 安装命令过时
- **位置**: 第 4.1 节 / 第 432-434 行
- **问题**: 使用旧式分离安装 `@typescript-eslint/eslint-plugin` 和 `@typescript-eslint/parser`
- **核实结果**: typescript-eslint 官方现在推荐统一安装 `typescript-eslint` 包（`pnpm add -D eslint typescript-eslint`），而非分开安装 plugin/parser。原文命令在 ESLint v9 flat config 环境下会导致配置复杂化
- **修改建议**: 更新为官方推荐命令：
  ```bash
  pnpm add -D eslint typescript-eslint eslint-plugin-vue prettier eslint-config-prettier vitest @vue/test-utils jsdom
  ```
  并同步更新配套的 `eslint.config.ts` 示例为 flat config 格式

## 🟡 建议改

### [Y1] "AI 协作账单"是伪数据
- **位置**: 第 6.5 节 / 第 674-682 行
- **问题**: 表格以精确到分钟和百分比（73%、58%、61%）呈现，制造"数据驱动"假象
- **核实结果**: 完全无来源，没有任何方法论、样本量或研究支撑。不同任务、团队、项目的差异极大
- **修改建议**: 删除具体数字，改为定性描述示例，或明确标注"以下数据为作者个人经验估计，非普遍性结论"。保留"纯模板/配置型任务 AI 节省最多，涉及外部 API 实时变化的部分 AI 反而容易拖慢节奏"这一洞察即可

### [Y2] 固定阈值缺乏通用依据
- **位置**: 第 6.1 节 / 第 635-636 行
- **问题**: "dev 启动超过 30 秒就值得评估迁移"、"CI 构建超过 10 分钟就值得引入远程缓存"
- **核实结果**: 完全基于作者个人经验，不同规模项目的可接受范围差异巨大
- **修改建议**: 改为条件性表述，如"dev 启动是否超过团队可接受范围？如果是，值得评估迁移到 Vite 系。CI 构建是否成为反馈瓶颈？如果是，值得引入 Turborepo / Nx 的远程缓存"

### [Y3] corepack 禁用理由表述不严谨
- **位置**: 第 1.3 节 / 第 67 行
- **问题**: "corepack 在团队全局环境里被本人禁用，原因是它会拦截命令"
- **核实结果**: Node.js 官方文档确实使用 "intercepts" 描述 corepack 行为，但核心问题不是"拦截"本身，而是自动版本切换和自动注入 `packageManager` 字段可能破坏团队工作流
- **修改建议**: 改为"corepack 会根据 `packageManager` 字段自动切换包管理器版本并自动注入该字段，在团队环境中可能导致版本不一致或工作流破坏"

### [Y4] `trigger` 字段无法证实为官方字段
- **位置**: 第 4.3 节 / 第 512 行
- **问题**: Skill frontmatter 中使用 `trigger` 字段
- **核实结果**: 官方 Skills 文档中未找到 `trigger` 字段说明。5.2 章已质疑该字段不是官方 frontmatter 字段
- **修改建议**: 删除 `trigger` 字段，或改为标准的 `description` 字段描述触发场景，并添加注释说明"触发机制需按实际 Claude Code 版本确认"
