# 修改建议: 4.4 Git 工作流

## 综合评估
- 整体质量: 命令和 flag 的准确性整体较高（`--worktree`、`-c`、`--resume`、`--from-pr`、`setup-token` 均真实存在），但 SFEIR Institute 的"研究数据"是最大硬伤，多处精确数字缺乏依据
- 问题分布: 🔴 高 4 / 🟡 中 4 / 🟢 低 3
- 是否阻塞发布: 否（删除 SFEIR 虚假数据 + 修正配置字段后可发布）

## 🔴 必改(高优先级:事实错误、逻辑硬伤)

### 1. SFEIR Institute "研究数据"全部为虚假营销数字
- **位置**: 第 2.1 节、第 4.1 节、第 10.1 节
- **原文摘录**:
  - "根据 SFEIR Institute 的研究数据，Claude Code 生成的提交信息平均包含 12 个单词...描述性提交信息能将代码审查时间缩短约 25%。"
  - "根据 SFEIR Institute 的统计，Claude Code 能在 30 秒内自动解决约 85% 的冲突"
  - "配置良好的 CLAUDE.md 能将团队 Git 工作流错误减少约 55%。"
- **问题**: SFEIR Institute 是法国 IT **培训机构**（非学术研究机构），其网站内容为教程和培训课程，无同行评审论文。"12 词 vs 4 词""25%""85%""95%""80%""60%""55%"——**全部是无实验依据的营销博客数字**。文档将其包装为"研究数据"和"统计"，严重误导读者，丧失学术诚信。
- **建议改写**: **删除所有 SFEIR "研究数据"和"统计"**，替换为：
  - 2.1 节: "描述性提交信息有助于审查者快速理解变更意图，是团队代码审查的最佳实践。"
  - 4.1 节: "Claude Code 通过读取冲突标记和双方变更历史，用自然语言解释冲突本质并提议解决方案。对于简单文本冲突，Claude 通常能直接给出合并建议；涉及业务逻辑的冲突，建议始终要求 Claude 解释原因后再确认。"
  - 10.1 节: "配置良好的 CLAUDE.md 能帮助 Claude 理解团队 Git 规范，减少因规范不一致导致的额外沟通成本。"
- **依据**: https://institute.sfeir.com/en/claude-code/ ; https://dev.to/creatman/i-stopped-claude-code-from-breaking-my-projects-heres-the-exact-setup-1agi（web-searcher 核实，SFEIR 为培训机构，无研究资质）

### 2. "AST 分析 + 合并"是夸大描述
- **位置**: 第 4.1 节 / 冲突解决表格
- **原文摘录**: "结构性冲突(import、函数) | AST 分析 + 合并 | 80%"
- **问题**: Claude Code 是基于 LLM 的文本处理工具，**没有内置 AST 解析器做结构化合并**。它通过读取 diff 上下文用 LLM 文本理解给出建议，但"AST 分析 + 合并"将 LLM 文本建议包装成代码语法分析能力，属于夸大。
- **建议改写**: "结构性冲突(import、函数) | 上下文理解 + 智能建议 | —"
- **依据**: https://code.claude.com/docs/en/cli-reference（web-searcher 核实，无 AST 相关功能）

### 3. `gitAttribution` 字段存疑
- **位置**: 第 2.4 节
- **原文摘录**:
  ```json
  {
    "includeCoAuthoredBy": false,
    "gitAttribution": false
  }
  ```
- **问题**: `includeCoAuthoredBy` 真实存在（多个社区来源确认），但 **`gitAttribution` 字段在公开搜索中未找到官方文档确认**，可能是作者自行编造的字段名。
- **建议改写**: 删除 `gitAttribution` 字段，或改为：
  ```json
  {
    "includeCoAuthoredBy": false
    // 其他 Git 相关配置请以官方文档为准
    // https://code.claude.com/docs/en/setup
  }
  ```
- **依据**: https://github.com/anthropics/claude-code/issues/5458 ; https://aiengineerguide.com/til/disable-co-author-in-claude-code/（web-searcher 核实，未找到 gitAttribution 字段）

### 4. `/commit-push-pr` 表述误导
- **位置**: 第 6.1 节
- **原文摘录**:
  ```
  User: /commit-push-pr
  会话已关联到 PR #143。之后可用 `claude --from-pr 143` 恢复此会话。
  ```
- **问题**: `claude --from-pr` 是**真实 CLI flag**（官方文档确认），但 `/commit-push-pr` 是**交互式 slash command**（会话内命令），不是 CLI 参数。文档将两者混为一谈，且写成 `User: /commit-push-pr` 会让读者误以为这是 shell 命令。
- **建议改写**:
  ```
  User: 提交并创建 PR

  Claude: [交互式命令] /commit-push-pr
         已分析变更，执行以下操作：
         ...
         会话已关联到 PR #143。之后可用 `claude --from-pr 143` 恢复此会话。
  ```
- **依据**: https://code.claude.com/docs/en/cli-reference（web-searcher 核实）

## 🟡 建议改(中优先级)

### 5. "200 毫秒"精确数字无来源
- **位置**: 第 1.3 节
- **原文摘录**: "连续按两次 `Esc` 键（Esc+Esc）可以在 200 毫秒内撤销所有正在进行的修改"
- **问题**: "200 毫秒"这个数字无来源，且"撤销所有修改"表述不准确——Esc 是中断当前回合，不是 guaranteed rollback，部分修改可能已在之前的 tool use 中写入。
- **建议改写**: "在 Claude 正在修改文件时，连续按两次 `Esc` 键可中断当前回合。部分情况下可回滚已做出的文件修改，但并非保证性撤销。"
- **依据**: web-searcher 未找到官方毫秒数据

### 6. 对话示例未标注为示意性
- **位置**: 第 1.1-1.3 节、第 2.1-2.3 节、第 3.1-3.3 节、第 4.1 节、第 5.1-5.3 节、第 6.3 节、第 7.1-7.5 节
- **问题**: 所有对话示例呈现为"Claude Code 总能正确理解用户意图并完美执行"，实际使用中 Claude 经常对"暂存""撤销""stash"的语义产生歧义。文档完全没有提及这种常见失败模式。
- **建议改写**: 在每个对话示例前添加统一标注：
  > 💡 **示意性示例**：以下对话展示了典型行为，实际输出可能因项目上下文、模型版本和提示词措辞而有所不同。
- **依据**: challenger [A]

### 7. PR 描述生成示例不严谨
- **位置**: 第 5.2 节
- **原文摘录**: "手动测试: `curl /api/search?cursor=eyJpZCI6MTB9`"
- **问题**: curl 命令缺少 scheme 和 host，不是可执行的 curl。作为示例不严谨。
- **建议改写**: "手动测试: `curl http://localhost:3000/api/search?cursor=eyJpZCI6MTB9`"
- **依据**: challenger [M]

### 8. 引用质量不足
- **位置**: 参考来源
- **问题**: 9 条来源中只有 2 条是 GitHub 官方文档，其余 7 条全是培训机构博客（SFEIR Institute、Developer Toolkit、DeployHQ、Eesel AI、Beam Terminal、DEV Community、Dan Does Code）。缺少 Anthropic 官方文档作为核心来源。
- **建议改写**: 优先引用 Anthropic 官方文档：
  - https://code.claude.com/docs/en/cli-reference — CLI 参考
  - https://code.claude.com/docs/en/desktop — Worktree/并行会话
  - https://code.claude.com/docs/en/setup — settings.json 配置
  社区博客降级为"补充参考"。
- **依据**: challenger [D][E][F]

### 11. `git push --force-with-lease` 缺乏风险提示
- **位置**: 第 8.4 节
- **原文摘录**: `git push --force-with-lease`
- **问题**: 对于新手而言这是危险操作，文档轻描淡写地放在 Worktree 小节里，缺乏风险提示。
- **建议改写**: 在命令旁添加注释：
  ```bash
  git push --force-with-lease  # ⚠️ 危险操作：会重写远程历史，确保无人基于此分支工作
  ```
- **依据**: challenger [T]

## 💡 建议补充

### 12. 补充 pre-commit hooks 讨论
- **位置**: 第 10.2 节
- **建议**: 文档没有讨论 `.husky`、lint-staged 等 pre-commit hook 如何与 Claude Code 的自动提交交互。这是实际高频冲突点。建议补充：
  - 当 Claude 自动提交时，pre-commit hooks 可能触发 lint/format，导致提交失败
  - 建议配置 Claude 在提交前手动运行 lint，或放宽 pre-commit 以非阻塞模式运行
- **依据**: challenger [R]

### 13. 补充 merge vs rebase 策略比较
- **位置**: 第 3.2 节
- **建议**: 文档直接让用户"变基到最新的 main"，没有解释 merge 与 rebase 的适用场景。建议补充简要对比：
  - rebase: 保持线性历史，适合个人功能分支
  - merge: 保留完整历史，适合团队协作分支
- **依据**: challenger [R]

### 14. 补充 Git LFS / 二进制文件冲突
- **位置**: 第 4 节
- **建议**: Claude Code 无法处理二进制冲突，但文档完全未提。建议补充：
  > ⚠️ **限制**: Claude Code 无法处理二进制文件冲突（如图片、PDF、编译产物）。遇到 Git LFS 管理的文件冲突时，需要手动解决。
- **依据**: challenger [R]

### 15. 补充 `git reflog` 恢复
- **位置**: 第 7 节
- **建议**: 比 bisect 更常用的误操作恢复工具 `git reflog` 完全未提。建议补充：
  ```bash
  # 查看最近的操作历史
  git reflog
  # 恢复到误操作前的状态
  git reset --hard HEAD@{n}
  ```
- **依据**: challenger [R]

## 📚 原文优点(明确保留)

1. **大量 CLI flag 描述准确**: `--worktree` / `-w`、`-c` / `--continue`、`--resume` / `-r`、`--from-pr`、`setup-token`——全部真实存在且有官方 CLI 参考支撑。challenger 对这些命令的质疑过于武断。
2. **Git Worktree 集成描述清晰**: 8.1-8.4 节对 Worktree 的概念、使用场景、Claude Code 的 `--worktree` flag、手动管理方法、最佳实践做了系统梳理。
3. **对话式 Git 操作直观**: 1.1-1.3 节的自然语言到 Git 命令的映射表格清晰，对不熟悉 Git 命令的初学者非常友好。
4. **提交信息生成流程完整**: 2.1-2.3 节覆盖了 diff 分析、Conventional Commits 规范、变更拆分，流程描述合理。
5. **冲突解决对话流程实用**: 4.1-4.2 节的冲突解释 → 分析 → 建议 → 确认流程，将复杂的合并冲突转化为可对话的交互。
