# 修改建议: 5.2 Skills——将重复工作流编码为可复用模板

## 综合评估
- 整体质量: 本章根基极虚。大量Skill基础设施可能是虚构的（plugin市场、.claude-plugin/、命名空间调用、npx skills、evals.json、Skills 2.0），多处精确数字无法追溯，frontmatter字段准确性存疑。结构类比（菜谱/厨具、渐进式披露）不错，但把社区草案和博客方法论包装成官方标准
- 问题分布: 🔴 高 7 / 🟡 中 5 / 🟢 低 3
- 是否阻塞发布: **是**（大量虚构功能、捏造数据、未验证URL，需重大修订）

## 🔴 必改(高优先级:事实错误、逻辑硬伤)

### 1. 大量Skill基础设施可能是虚构的
- **位置**: 第 4.1 节、第 5.1 节、第 5.3 节
- **原文摘录**:
  - `/plugin marketplace add anthropics/skills`
  - `/plugin install document-skills@anthropic-agent-skills`
  - `npx skills add https://github.com/anthropics/skills --skill xlsx`
  - `.claude-plugin/` 目录 + `plugin.json`
  - 命名空间调用: `/my-team-skills:code-review`
- **问题**: **全部未在公开搜索中找到官方文档支撑**。如果 plugin 市场、`.claude-plugin/` 目录结构、`npx skills` CLI 工具、命名空间调用语法不存在，整章的"标准化工作流"核心主张就站不住脚。
- **建议改写**: **删除所有未经官方验证的 plugin 市场、命名空间调用、`.claude-plugin/`、`npx skills` 相关内容**。保留已确认的内容：
  - Skill 存储位置：企业级/个人级(`~/.claude/skills/`)/项目级(`.claude/skills/`)
  - `SKILL.md` + YAML frontmatter（官方确认字段）
  - GitHub `anthropics/skills` 仓库（真实存在）
- **依据**: web-searcher 未找到任何官方来源

### 2. "Skills 2.0"和 `evals/evals.json` 未获官方确认
- **位置**: 第 3.4 节、第 2.1 节
- **原文摘录**:
  > "Skills 2.0 引入了内置的 eval 框架...`evals/evals.json`"
- **问题**: 搜索未找到官方文档或 `anthropics/skills` 仓库确认 Skills 2.0 版本号或内置 eval 框架。
- **建议改写**: **删除"Skills 2.0"命名和 `evals/evals.json` 相关内容**。 Skill 测试可改为通用描述："创建 Skill 后，通过实际对话测试触发条件和执行流程，验证输出是否符合预期。"
- **依据**: web-searcher 未找到独立来源

### 3. 周安装量数据是捏造
- **位置**: 第 4.3 节
- **原文摘录**:
  | find-skills | ~787K |
  | web-design-guidelines | ~133K |
  | superpowers | ~40K |
  | remotion-best-practices | ~117K |
- **问题**: 787K 周安装量对于小众 CLI 工具高得离谱。react-best-practices 和 firecrawl 安装量标为 "-"，说明数据不完整且随意。**全部无来源**。
- **建议改写**: **删除整列"周安装量"**，改为 "社区贡献的 Skill 示例"表格，仅列出 Skill 名称、作者和功能描述。
- **依据**: web-searcher 未找到独立来源

### 4. "Vercel 实验"是无来源虚构
- **位置**: 第 7.3 节
- **原文摘录**:
  > "Vercel 的实验表明：对于通用知识，直接嵌入 CLAUDE.md 的 8KB 压缩文档索引比 Skill 的按需加载效果更好（100% vs 79% 通过率）"
- **问题**: 未找到 Vercel 官方博客或技术文章确认该实验。"通过率"指代不明，三个精确数字无任何来源。
- **建议改写**: 删除具体数字，改为 "对于通用知识，直接嵌入 CLAUDE.md 通常比 Skill 的按需加载效果更稳定，因为 CLAUDE.md 在每次会话开始时完整加载。"
- **依据**: web-searcher 未找到独立来源

### 5. `agent`、`effort`、`shell` 等 frontmatter 字段未获官方确认
- **位置**: 第 2.3 节
- **原文摘录**:
  | `effort` | 否 | 努力程度：`low`、`medium`、`high`、`xhigh`、`max` |
  | `shell` | 否 | 内联 shell 命令使用的 shell |
  | `agent` | 否 | 配合 `context: fork` 使用的子代理类型 |
- **问题**: `name`、`description`、`tools` 是官方确认字段。但 `agent`、`effort`、`shell`、`context` 在公开搜索中未找到官方文档确认。`effort` 听起来像 Claude API 参数而非 Skill frontmatter。
- **建议改写**: 在表格上方添加声明：
  > 📌 **字段可用性声明**：以下字段列表基于社区实践整理。`name`、`description`、`tools` 为官方确认字段。其他字段可能随版本更新而变化，请以 Anthropic 官方 Skills 文档为准。
  并删除未确认字段（`effort`、`shell`、`agent`、`context`），或将其移至"社区 rumored 字段"小节。
- **依据**: web-searcher 未找到官方确认

### 6. `!`command`` 语法第三次出现，仍无官方来源
- **位置**: 第 2.5 节
- **原文摘录**:
  > "使用 `` !`command` `` 语法可以在 Skill 内容发送给 Claude 之前执行 shell 命令"
- **问题**: 这是本书第三次出现该语法（4.5、5.1、5.2），每次上下文不同，均无官方来源支撑。如果官方不支持，三个章节的核心示例全部失效。
- **建议改写**: 在示例前添加注释：
  > 📌 **语法可用性声明**：以下 `!`command`` 语法基于社区实践，官方支持情况请以 Anthropic 文档为准。如不可用，可使用 Skill 内的 Bash 工具调用替代。
- **依据**: web-searcher 未找到官方确认

### 7. "Agent Skills 开放标准已被 30+ 平台采纳"过度拔高
- **位置**: 第 5.3 节
- **原文摘录**:
  > "Skills 遵循 [Agent Skills](https://agentskills.io) 开放标准，该标准已被 30+ 平台采纳..."
- **问题**: agentskills.io 网站真实存在，但"30+ 平台"这个数字来自第三方博客，**非 Anthropic 官方直接声明**。Cursor、GitHub Copilot、Codex CLI 等主流工具是否官方支持该格式，需要各自官方文档交叉验证。
- **建议改写**:
  > "Skills 遵循 [Agent Skills](https://agentskills.io) 倡议，据第三方报道已有部分平台实验性支持。但截至文档撰写时，主流工具（Cursor、GitHub Copilot、Codex CLI 等）均有各自的配置格式，Agent Skills 尚未成为跨平台统一标准。"
- **依据**: https://agentskills.io ; https://byteiota.com/agent-skills-standard-microsoft-openai-adopt-in-48-hours/（web-searcher 核实，"30+平台"来自第三方博客）

## 🟡 建议改(中优先级)

### 8. `${CLAUDE_SESSION_ID}`、`${CLAUDE_SKILL_DIR}` 等变量未确认
- **位置**: 第 2.4 节
- **原文摘录**:
  | `${CLAUDE_SESSION_ID}` | 当前会话 ID |
  | `${CLAUDE_SKILL_DIR}` | Skill 文件所在目录 |
- **问题**: 未在官方 Skills 文档中找到这些变量替换语法的确认。`${CLAUDE_SKILL_DIR}` 这种命名风格尤其可疑。
- **建议改写**: 删除未确认变量，仅保留官方确认的 `$ARGUMENTS` 和命名参数 `$name`。或添加声明："变量替换语法请以官方文档为准。"
- **依据**: web-searcher 未找到官方确认

### 9. "2%上下文窗口=16,000字符"单位混淆且无来源
- **位置**: 第 7.3 节
- **原文摘录**:
  > "所有 Skill 的 description 共享约 2% 的上下文窗口（约 16,000 字符）"
- **问题**: 上下文窗口以 token 计量，不是字符。如果 200K token 的 2% = 4K tokens，约等于 12K-16K 字符（取决于语言），计算本身有合理性，但"2%"和"16,000 字符"均无官方来源。
- **建议改写**: 删除具体数字，改为 "所有 Skill 的 description 共享有限的上下文预算。安装过多 Skill 会导致 description 被截断，建议每个项目保持适量的自动触发 Skill。"
- **依据**: web-searcher 未找到官方来源

### 10. frontmatter 表中 `name` 标注为"否"与正文矛盾
- **位置**: 第 2.3 节
- **原文摘录**: 表格中 `name` 标注"否"（非必需），但第 2.2 节说 `name` "成为 /slash-command"。
- **问题**: 如果 name 省略，slash command 如何工作？表格与正文自相矛盾。
- **建议改写**: 将 `name` 改为"是"（必需），或补充说明"省略时使用目录名作为 slash command"。
- **依据**: challenger [I]

### 11. 多个引用 URL 未验证
- **位置**: 参考来源
- **原文摘录**:
  - `https://claude.com/blog/skills`

  - 将 `claude-world.com` 的标注改为"社区翻译/整理"

- **依据**: web-searcher 未直接验证

## 📚 原文优点(明确保留)

1. **Skills 与 MCP 的对比清晰**: 1.2 节的"菜谱 vs 厨具"类比直观，帮助读者理解 Skills（如何做）和 MCP（用什么做）的定位差异。
2. **Skill 设计原则实用**: 7.2 节的渐进式披露（三级加载）、description 是触发器、聚焦"推 Claude 出舒适区"的信息、使用文件系统作为上下文工程——这些原则对 Skill 编写者有实际指导价值。
3. **反模式覆盖全面**: 7.3 节的 description 预算问题、YAML 多行 description、Skill 与 CLAUDE.md 边界——覆盖了最常见的 Skill 误用。
4. **实际案例丰富**: 6.1-6.3 节的代码审查、周报生成、数据清洗三个案例覆盖了不同场景，展示了 Skill 的实际应用方式。
5. **适用场景判断清晰**: 1.3 节和 7.1 节明确了何时使用 Skills vs 直接对话 vs CLAUDE.md，帮助读者做出正确选择。
